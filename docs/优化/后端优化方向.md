# 后端优化方向

> 整理时间：2026-09-29 ｜ 基于 2026-09 代码现状梳理，按「收益/改动比」排序
> 对应旧文档：《项目完善计划.md》（功能层面，本篇聚焦后端工程质量）

## P1. 阻塞事件循环（最优先：改动小、用户体感提升最明显）

**问题**：所有路由均为 `async def`，但内部全是同步阻塞 I/O。最严重的是三处 LLM 同步调用：

| 端点 | 位置 | 阻塞时长 |
|---|---|---|
| `POST /api/trial/report` | `trial_service.generate_report` | 10-30s |
| `POST /api/quiz/generate` | `question_generator.generate` | 10-30s |
| `POST /api/exam/submit` | `exam_service.analyze_weaknesses` | 5-20s |

LLM 调用期间**整个事件循环被卡死**，所有并发请求（含 SSE 流式问答 `/api/query/stream`）全部排队。

**修复方案**：
1. 纯阻塞路由把 `async def` 改为 `def` —— FastAPI 自动将其放入线程池执行，事件循环不再被阻塞（改动量：改函数声明 + 去掉无意义的 await）；
2. `POST /api/query/stream`（SSE）必须保持 `async def`，内部对 agent 的同步调用包 `asyncio.to_thread` / `run_in_executor`；
3. Neo4j/SQLite 读写密集的路由（`/api/quiz/answer`、`/api/review/*`）同样受益于改 `def`。

**验证**：压测脚本并发打 LLM 端点的同时测 `/api/health` 响应时间（修复前会从毫秒级劣化到数十秒）。

## P2. `web/graph_rag_web.py` 瘦身（可维护性）

**问题**：1200+ 行 god file，所有路由 + 服务装配挤在一个文件；每个 handler 重复「global 声明 + 懒初始化 + try/except」三段样板。

**方案**：
1. 按模块拆 `APIRouter`：`web/routers/{query,quiz,exam,review,trial,dashboard,graph}.py`，主文件只保留 app 装配与中间件；
2. 懒初始化收敛为 FastAPI 依赖：`svc: TrialService = Depends(get_trial_service)`，一个 `get_*` 函数替代每处样板（顺带解决懒初始化非线程安全、并发首请求可能双建服务的问题——加 `threading.Lock` 或启动即初始化）;
3. `@app.on_event("startup"/"shutdown")` 已废弃 → 改 `lifespan` 上下文管理器（消掉测试输出的 4 个 DeprecationWarning）。

**注意**：拆分需同步更新 `tests/integration/test_api.py` 对 `web_mod.xxx` 全局变量的 patch 目标（改为 patch router 模块的依赖获取函数，或保留 app 级单例注入点）。

## P3. Cypher 查询批量化

**问题**：多处 N+1 往返：

| 位置 | 现状 | 优化 |
|---|---|---|
| `quiz_service.add_question` | 每条 reference 单独一次 `MATCH...MERGE` | UNWIND 批量建边 |
| `trial_service._fetch_layer_pools` | 按层 5 连查 | `MATCH (q:MCQuestion) RETURN q.layer, collect(q.id)` 一次拿全 |
| `quiz_service.get_chapter_structure` | 多轮聚合查询 | 合并为一轮 `WITH` 聚合 |
| `question_generator` references 回联 | 逐题逐 reference | 同上 UNWIND |

单次几十毫秒不痛，但叠加在答题/出题链路上是纯浪费，且占用连接池。

## P4. 存储层历史包袱

**4a. `quiz_storage` 全局 JSON（跑正式试用前建议处理）**
- 每次 `mark_done`/`add_wrong` 全量重写文件（O(n) 写放大）；
- **不分用户**：已做/错题记录全局共享，多被试试用会互相污染——前测-后测的"学习行为"虽走 SQLite 不受影响，但被试在 `/quiz` 页看到的"已做/错题"是所有人的并集；
- 方案：迁到 MasteryTracker 新表（`quiz_done`/`quiz_wrong`，按 session_id 隔离），API 不变，前端无感。

**4b. MasteryTracker 单连接 + 全局锁（优先级最低）**
- 读写全串行；WAL 已开，当前规模（单机、几十用户）够用；
- 若后续并发上来：读操作走每线程连接（`sqlite3` + thread-local）或换 `aiosqlite`。

## 暂缓项（已有结论）

- **MCQ -18pp**：MCQ 场景精简作答模式，用户决定暂缓（对比实验报告已有局限性声明）；
- 限流器/会话为进程内存态：单进程部署无碍，多副本部署时才需要 Redis 化。

## 建议实施顺序

1. P1 一天内可完成（含压测验证），先做；
2. P2 纯重构、有测试兜底（212 项），适合作为一个独立提交；
3. P4a 在招募真实被试前完成，避免试用数据污染；
4. P3 / P4b 择机顺手做。
